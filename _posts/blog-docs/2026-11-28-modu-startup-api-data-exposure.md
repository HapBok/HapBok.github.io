웹사이트에서 정보를 비공개로 설정하면 다른 사람에게 보이지 않을 것이라고 기대한다. 그렇다면 개발 과정에서는 이 기대를 어떻게 보장해야 할까?

2026년 6월 발생한 모두의창업 정보 유출 사고를 조사하면서 이 질문을 살펴봤다. 평소 자주 보는 노말틱 채널에도 이 사건을 API와 개발 방식의 관점에서 설명한 [「모두의창업, 유출 사고? 무슨 일인가. 문제있는 개발 패턴들」](https://www.youtube.com/watch?v=stPKmb1sLPw) 영상이 있다.

이번 글에서는 영상 이후 공개된 정부 조사 결과를 함께 확인해, 비공개 정보가 노출된 원인과 대응을 정리했다. **조사 기준일은 2026년 11월 28일이며, 분석 대상은 6월 공식 플랫폼 사고다.** 실제 서비스에 API 요청을 보내거나 개인정보를 수집하는 실험은 하지 않았다.

## 어떤 정보가 유출됐는가

중소벤처기업부의 초기 설명에 따르면, 6월 15일 합격자 프로필 공개 이후 비공개 정보에 대한 접근 시도가 확인됐다. 당일 오후 이용자 문의로 상황을 인지하고 오후 4시경 해당 접근 경로를 차단했으며, 6월 18일에는 대상자 통지와 신고를 진행했다. [중소벤처기업부 6월 18일 설명자료](https://www.mss.go.kr/site/smba/ex/bbs/View.do?bcIdx=1069139&cbIdx=87)

7월 31일 조사 결과 브리핑에서는 합격자 5,000명의 이메일 주소, 심사평, 200자 이내 창업 아이디어 요약 정보가 유출됐다고 설명했다. 일부 API에 비공개 정보가 포함돼 있었고, 외부 주체가 이를 수집하는 과정에서 유출이 발생했다는 것이다.

또한 정보가 암호화돼 있었지만 암호화 키도 함께 유출돼 복호화가 가능했다고 밝혔다. [중소벤처기업부 7월 31일 조사 결과](https://www.korea.kr/briefing/policyBriefingView.do?newsId=156772942)

## 화면에 표시하는 것과 서버가 전달하는 것

이 사건을 이해하려면 웹페이지가 데이터를 받아오는 과정을 알아야 한다.

웹사이트의 화면을 구성하는 부분을 프런트엔드, 서버에서 데이터와 기능을 처리하는 부분을 백엔드라고 한다. 프런트엔드는 API를 통해 필요한 정보를 요청하고, 서버가 반환한 데이터를 화면에 표시할 수 있다. API는 프로그램 사이에서 기능과 데이터를 주고받기 위한 인터페이스다.

문제는 서버가 전달한 정보 중 일부를 화면에서만 숨기는 경우다.

다음은 실제 사고의 응답을 재현한 것이 아닌 개념 설명용 예시다.

```text
서버가 전달한 정보
닉네임 + 비공개 이메일 + 비공개 아이디어

화면에 표시한 정보
닉네임
```

화면에 이메일과 아이디어가 보이지 않더라도, 데이터는 이미 브라우저에 도착해 있다. 화면 표시 여부만으로는 서버가 전달한 정보에 대한 접근을 막을 수 없다.

**비공개 정보라면 요청자가 열람할 권한이 있는지 서버에서 확인하고, 권한이 없을 때는 응답에서 제외해야 한다.**

OWASP도 API가 반환하는 객체의 각 속성에 대해 접근 권한을 확인하고, 필요한 정보만 반환하도록 권고한다. 이번 사건은 이 원칙을 적용해 이해할 수 있다. 이는 공개된 원인과 OWASP 지침을 연결한 분석이며, 정부가 사건에 해당 분류를 공식 부여했다는 뜻은 아니다. [OWASP API3:2023 - 객체 속성 수준의 접근 통제](https://owasp.org/API-Security/editions/2023/en/0xa3-broken-object-property-level-authorization/)

## 암호화돼 있었는데 왜 보호되지 못했을까

공식 조사 결과에서 눈에 띄는 부분은 암호화 키도 함께 유출됐다는 설명이다.

암호화는 데이터를 읽을 수 없는 형태로 바꾸고, 적절한 키를 가진 주체가 복호화하도록 만드는 방식이다. 그런데 정보를 받아서는 안 되는 주체가 암호문과 복호화에 필요한 키를 모두 얻을 수 있다면, 암호화만으로 기대한 보호 효과를 얻기 어렵다.

따라서 이번 사고를 분석할 때는 두 문제를 함께 봐야 한다.

첫째, API가 비공개 정보를 외부에 전달했다는 점이다. 둘째, 전달된 정보를 복호화할 수 있는 키까지 노출됐다는 점이다. 이는 암호화 알고리즘이 깨졌다는 설명과는 구분된다. [암호화 키 유출에 관한 공식 설명](https://www.korea.kr/briefing/policyBriefingView.do?newsId=156772942)

이 구조에서는 암호화를 강화하는 조치와 함께, 애초에 요청자에게 어떤 정보를 전달해도 되는지 결정하는 접근 통제가 필요하다.

## 어떤 대응이 이루어졌는가

정부는 후속 브리핑에서 API에 포함되는 정보를 최소화하고 불필요한 기능을 삭제했으며, 암호화 체계와 비정상 접근 탐지·차단 기능을 강화했다고 밝혔다. 개인정보 열람 권한과 보유·파기 기준도 정비했다고 설명했다. [7월 31일 보안 강화 조치 발표](https://www.korea.kr/briefing/policyBriefingView.do?newsId=156772942)

원인과 대응의 관계는 다음과 같이 정리할 수 있다. 아래 표의 대응 방향은 공식 조치와 공개된 원인을 바탕으로 재구성한 것이다.

| 문제 | 필요한 대응 |
| --- | --- |
| 비공개 정보가 API 응답에 포함됨 | 서버에서 권한을 확인하고 허용된 필드만 반환 |
| 데이터와 복호화 키가 함께 노출됨 | 키의 배포·저장·접근 범위 재검토 |
| 반복적인 정보 수집 가능 | 비정상 접근 탐지와 대량 조회 제한 |
| 필요 이상의 정보 보유 | 보유 기간과 파기 기준 정비 |

이 중 조회 제한은 대량 수집으로 피해가 커지는 것을 줄이는 데 도움이 된다. 그러나 권한 없는 요청에 비공개 정보를 반환하는 문제 자체를 해결하지는 못한다. 적은 횟수의 요청에서도 비공개 정보가 전달되지 않도록 해야 한다.

## 보완이 필요한 부분은 어떻게 검증할까

이 사건의 개선 여부를 검증한다면 화면과 API 응답을 함께 확인해야 한다.

예를 들어 동일한 프로필을 비로그인 이용자, 다른 일반 회원, 정보 소유자가 조회할 때 각자 받을 수 있는 정보가 서비스 정책에 맞아야 한다. 또한 공개 설정을 비공개로 변경한 뒤 관련 API 전체에 그 정책이 반영되는지도 살펴봐야 한다.

이때 테스트의 성공 기준은 화면에서 항목이 사라지는 것에 그치지 않는다. 권한 없는 요청자가 받는 응답에도 해당 정보가 없어야 한다.

API마다 공개 정책을 따로 구현했다면 일부 경로만 수정되고 다른 경로가 남을 수 있다. 따라서 비슷한 데이터를 반환하는 API와 공통 응답 처리 방식까지 함께 검토하는 것이 필요하다. 이 내용은 공개된 원인에 기반한 검증 제안이며, 실제 플랫폼의 수정 상태를 직접 확인한 결과는 아니다.

## 조사하면서 남긴 구분

영상은 6월 당시의 정보를 설명하고, 정부 브리핑은 이후 조사 결과를 포함한다. 따라서 영상에서 설명한 내용을 그대로 현재의 최종 조사 결과로 옮기지 않고 자료의 발표 시점을 확인했다.

또한 11월에는 모두의창업 참가자가 이용하던 민간 AI 솔루션 업체에서 별도 사고가 발생했다. 중기부는 이를 공식 플랫폼에서 발생한 추가 해킹과 구분했다. 이번 글의 분석 대상은 **6월 공식 플랫폼 사고**이며, 두 사건을 같은 침입 경로의 재발로 묶지 않았다. [11월 사고에 관한 중기부 설명](https://www.korea.kr/briefing/actuallyView.do?newsId=148976050)

수집 주체의 고의성이나 법적 책임도 기술적 원인과 구분해야 한다. 이번 글에서는 확인한 공식 자료를 넘어 최종 수사 결론이나 책임 소재를 판단하지 않았다.

## 비공개 기능의 완료 기준

이 사건을 조사하며 비공개 기능을 확인하는 기준을 구체적으로 정리할 수 있었다.

사용자가 비공개로 설정했다면, 그 정책은 화면뿐 아니라 서버가 데이터를 반환하는 단계에도 적용돼야 한다. 암호화와 접근 통제도 각각의 역할을 확인해야 한다. 암호화된 데이터라도 키를 누가 얻을 수 있는지에 따라 보호 효과가 달라진다.

앞으로 유사한 기능을 살펴볼 때는 "화면에서 보이지 않는가?"와 함께 **"권한 없는 요청자에게 데이터가 전달되는가?"**를 확인해야겠다.

이번 분석에서 직접 확인한 것은 공개 자료의 설명과 조치 발표다. 실제 서비스의 응답이나 수정 코드를 검증하지 않았으므로, 접근 통제가 현재 완전하게 작동한다고 평가한 것은 아니다.
