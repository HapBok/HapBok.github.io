오늘은 Keycloak의 OTP 인증 우회 취약점 **CVE-2026-135768**을 정리했다. 비밀번호로 로그인한 세션이 있다는 사실과, 추가 인증까지 마쳤다는 사실은 다르다. 이번 문제는 기존 로그인 세션을 다시 사용할 때 이 차이를 제대로 검사하지 못한 사례다.

선정한 X 게시물은 **2026년 11월 25일 11:08 KST**에 올라와 조사 시점 기준 최근 24시간 안에 해당한다. 오늘 새로 확인한 소식은 CVE 기록 공개와 공식 X 알림이다. Red Hat 공지의 공개일 표기는 11월 23일이며, 실제 공격 발생일을 뜻하지 않는다.

- **분야:** 인증 · SSO · 다중 요소 인증
- **선정 이유:** 기존 로그인 세션의 신뢰 수준과 애플리케이션이 요구하는 인증 수준 사이의 경계를 이해하기 위해 선정했다.
- **한 줄 요약:** OTP를 요구하는 특정 Keycloak 클라이언트 정책에서 요청에 인증 수준을 명시하지 않으면, 비밀번호만으로 만든 SSO 세션이 수락돼 추가 인증을 우회하고 실제보다 높은 인증 수준을 주장하는 토큰을 받을 수 있다.
- **X 출처:** CVE Program 공식 신규 CVE 알림 계정 `@CVEnew`, **2026-11-25 11:08 KST**, [개별 게시물](https://x.com/CVEnew/status/2125411176985317682). 발견자의 기술 분석 글은 아니며, 공식 CVE 웹사이트의 계정 링크와 프로필을 대조했다.
- **원문 출처:** X에서 연결한 [CVE-2026-135768 공식 기록](https://www.cve.org/CVERecord?id=CVE-2026-135768), **2026-11-25 공개·업데이트**, CNA(취약점 식별 번호를 발급하고 정보를 등록하는 기관)는 Red Hat이다.
- **보완한 공식 자료:** [Red Hat CVE-2026-135768 공지](https://access.redhat.com/security/cve/cve-2026-135768), **공개일 표기 2026-11-23**, 최종 수정 **2026-11-25 03:42:02 UTC → 12:42:02 KST**. 원인·악용 조건·제품별 수정 상태는 이 공지와 대조했다.

## 핵심 내용

- **원래 하는 일:** SSO(Single Sign-On)는 이미 로그인한 세션을 다른 애플리케이션의 인증에도 사용하는 방식이다. OTP는 일회용 비밀번호를 이용한 추가 인증이다. 이 취약점은 OTP를 요구하는 높은 인증 수준의 흐름을 클라이언트 정책으로 지정한 경우에 발생한다. [Red Hat 설명](https://access.redhat.com/security/cve/cve-2026-135768#cve-description)
- **문제의 조건:** 요청이 특정 인증 수준을 명시하지 않으면 기존의 비밀번호 전용 SSO 세션을 잘못 수락할 수 있다. Red Hat은 명시적인 ACR(Authentication Context Class Reference, 인증 수준을 나타내는 값)이 없는 요청에서 인증 흐름의 요구사항을 제대로 강제하지 못하는 것이 원인이라고 설명한다. 공격자에게는 사용자의 비밀번호 또는 세션에 대한 접근이 필요하다. [Red Hat 판단](https://access.redhat.com/security/cve/cve-2026-135768#cve-statement)
- **영향:** 추가 인증을 건너뛰고, 실제 검증한 것보다 높은 인증 수준을 주장하는 토큰을 얻을 수 있다. Red Hat은 특정 정책 구성과 요청 조건이 필요하다는 이유로 심각도를 **Moderate**, CVSS 3.1 점수를 **6.8**로 평가했다. CVE의 원인 분류는 **CWE-287: 부적절한 인증**이다. [공식 CVE 기록](https://www.cve.org/CVERecord?id=CVE-2026-135768)

## 공격과 방어 관점

**공격자 관점에서 중요한 경계는 비밀번호 인증과 추가 인증 사이에 있다.** 정상적인 흐름이라면 비밀번호만 확인한 세션으로 OTP까지 완료했다는 신뢰를 얻어서는 안 된다. 기존 세션을 재사용하는 과정에서 추가 인증 요구가 빠지면, 토큰을 받는 애플리케이션은 실제로 수행되지 않은 인증을 수행한 것으로 믿을 수 있다. 이는 공식 설명을 바탕으로 정리한 신뢰 경계의 해석이다.

영향을 판단할 때는 Keycloak 사용 여부에 더해 **OTP 흐름을 선택하는 클라이언트 정책, 기존 비밀번호 SSO 세션, 명시적 ACR이 없는 요청**이 만나는지 살펴봐야 한다. 모든 Keycloak 로그인에서 조건 없이 OTP를 우회할 수 있다는 뜻으로 읽으면 안 된다. [악용 조건과 원인](https://access.redhat.com/security/cve/cve-2026-135768#cve-statement)

**확인한 공식 공지에는 수정 버전과 보안 업데이트 번호가 아직 제시돼 있지 않다.** 제품 표에서 Red Hat Build of Keycloak의 관련 구성 요소는 `Affected`, Red Hat Single Sign-On 7은 `Fix deferred`로 표시된다. 후자는 수정이 연기됐다는 상태이며, 수정 완료를 뜻하지 않는다. 커뮤니티 Keycloak의 구체적인 버전별 영향 범위와 수정 릴리스를 이 자료만으로 확정하지 않았다. [제품별 상태](https://access.redhat.com/security/cve/cve-2026-135768#cve-affected-packages)

Red Hat의 완화책 항목은 대응책이 없거나, 현재 방안이 배포 용이성·적용 범위·안정성 기준을 충족하지 못한다고 설명한다. 따라서 요청에 ACR을 추가하면 문제가 완전히 해결된다고 단정할 근거는 부족하다. 운영 환경에서는 해당 정책과 요청 구성을 파악하고 공급사의 수정 공지를 추적할 필요가 있다. 허가된 테스트 환경에서 실제 OTP 수행 여부와 발급 토큰의 인증 수준이 일치하는지 비교하는 것은 내가 정리한 검증 방향이며, 공급사가 보장한 완화책이나 이번에 실행한 실험은 아니다. [공식 완화책 상태](https://access.redhat.com/security/cve/cve-2026-135768#cve-mitigation)

## 확인 상태

- **확인한 내용:** 취약점·CVE 기록 공개, 공식 X 알림, 원인과 악용 조건, Red Hat 제품별 수정 상태를 확인했다. Red Hat은 발견·제보자로 Blake Burkhart와 Defense Unicorns를 명시한다.
- **미확인:** 확인한 공식 기록과 공지에서는 공격 PoC, 실제 악용·피해 사례, 수정 릴리스, 전용 탐지 규칙을 확인하지 못했다. 비공개 또는 다른 곳에 존재하지 않는다는 뜻은 아니다. 사건 발생일과 피해 규모도 미확인이다.
- **정리 범위:** 공개 문서를 읽고 정리했다. 소스 코드의 구체적인 결함 위치, 공격 재현, 패치 전후 실행 결과는 이번에 검증하지 않았다.
